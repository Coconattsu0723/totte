## 制作区分

小規模カフェの店舗運営を想定した、架空の売上・在庫管理Webアプリです。企画から公開までを一貫して行い、画面を見せるだけでなく、在庫不足の発見から発注、入荷、在庫反映まで操作できるデモとして制作しました。

実際のPOS連携、認証、サーバー、仕入先への送信は実装せず、ブラウザ内の架空データで業務フローを再現しています。

## サービス概要

「totte」は、3店舗ほどを運営する小規模カフェの店長向けに、売上・在庫・発注を一つにまとめる業務Webアプリです。コンセプトは「必要な情報に手が届き、日々の業務を扱いやすくする」、コピーは「お店の毎日を、ひとつに整える。」としました。

ダッシュボード、売上分析、在庫管理、発注管理の4画面を用意し、店舗ごとの現在状況と次に必要な操作を同じ流れの中で確認できます。

## ターゲット

3店舗ほどを展開する小規模カフェの各店舗店長を想定しています。開店前の在庫確認、営業後の売上確認、補充手配を日常的に行い、売上と在庫を別々の画面や資料で確認しているため、発注判断に時間がかかっている利用者です。

PCでの営業状況確認を中心としながら、店舗内でタブレットやスマートフォンから確認・操作する場面にも対応しました。

## 制作目的

課題は、売上と在庫が分かれていることで、営業状況を踏まえた補充判断と発注着手に時間がかかることです。そこで、当日の営業状況、補充が必要な在庫、入荷待ちの発注を一つの画面群へまとめました。

主要な操作は、在庫不足を見つけ、店舗と品目を引き継いだ発注を作成・確認・確定することです。さらに、入荷処理によって在庫へ数量を反映し、入荷済みの発注を二度処理できないところまで設計しました。

## デザインコンセプト

業務画面としての可読性を保ちながら、カフェの空気感に合う明るさと温かみを加えました。薄いウォームグレーの背景、白いカード、深いグリーンの主要操作、チャコールの文字を基本としています。

注意はアンバー、入力エラーは赤、完了はグリーンで示しますが、色だけに依存せず、アイコンと「要補充」「発注済み」「入荷済み」などの文言を併用しました。

ロゴは「totte＝取っ手」と「必要な情報に手が届く」という意味から、取っ手のアーチと小文字の `t` を組み合わせたシンボルを制作しました。品目画像は、店舗で実物の資材を撮影して切り抜いたような背景透過素材で統一しています。

## 情報設計

ダッシュボードでは、当日の売上・客数・客単価を最初に置き、次に対応が必要な在庫、過去7日間の売上推移、入荷待ちの発注を配置しました。モバイルでは、数値の直後に要補充の在庫を移動し、画面が狭くても緊急度の高い情報へ先に到達できる順序にしています。

在庫状態と発注状態は別々に扱いました。在庫では「現在庫が補充基準以下か」、発注では「発注済みか入荷済みか」を明示し、現在の状況と次の操作を混同しない構成にしています。

## 発注・入荷導線の工夫

ダッシュボードの在庫アラートから発注を始めると、店舗と品目をフォームへ引き継ぎます。フォーム内には現在庫、補充基準、既存の入荷待ち数量を表示し、重複発注へ気づけるようにしました。

発注は「内容入力 → 確認 → 発注完了 → 入荷待ち → 入荷済み」の5段階で示します。入荷確認では「現在庫＋今回の入荷＝反映後」を数式状に並べ、確定後は在庫数と発注状態を同時に更新します。入荷済みの操作は「処理済み」として無効化し、二重処理を防いでいます。

## レスポンシブ対応で工夫した点

1440pxを制作の主軸とし、375 / 390 / 768 / 1024 / 1366 / 1440pxで確認しました。1366 / 1440pxは224pxのサイドバーと多列表、1024pxは184pxのサイドバーと優先列へ絞った表、768pxは72pxのナビゲーションレールとカード一覧、375 / 390pxは上部ヘッダーと下部ナビゲーションへ切り替えています。

公開後QAでは、768pxの発注ボタンと1024pxの発注表で不自然な文字折り返しを発見しました。ボタン文言を途中改行させず、1199px以下の発注表では補助情報である発注日を省略し、Pencilの1024px正本と同じ優先列へ調整しました。

## 共通パーツ化した部分

ナビゲーション、店舗選択、ボタン、KPIカード、ステータス、商品サムネイル、データ表、モバイルカード、モーダル、通知を共通化しました。色、余白、角丸、境界線もCSS変数で管理し、画面ごとに同じ役割のUIが異なる見た目にならないようにしています。

品目データは在庫、ダッシュボード、発注一覧、モーダルから同じ定義を参照します。これにより、名称、単位、仕入先、画像、在庫数の対応を一箇所で管理しています。

## HTML / CSS / JavaScriptで工夫した点

外部フレームワークを使わず、HTML / CSS / Vanilla JavaScriptで構成しました。URLのハッシュで4画面を切り替え、店舗、選択日、在庫、発注状態をブラウザ内へ保存しています。

発注数量は1以上の整数、入荷予定日は対象日以降を必須とし、項目別エラーとフォーム全体の要約を表示します。モーダルは確認、処理中、完了を切り替え、処理中は重複操作を無効化しました。警告や状態には文言とアイコンを併用し、キーボードフォーカスとEscapeによる閉じる操作も確認しています。

## 自分で判断・修正した点

初期の品目画像は、パッケージの横に豆や粉などを置いた演出的な見せ方になり、実店舗の在庫管理画面としてはAI生成らしさが強く見えました。そこで、資材1点のみを背景透過で撮影した想定へ変更し、14品目を同じ条件で作り直しました。

ロゴは実画面へ配置した後、文字との重なりや背景色の差による四角い跡を確認しました。コンポーネント自体の背景を透明にし、画面幅ごとにサイズとロゴ形式を調整しました。

また、公開後も本番URLを6つの代表幅で確認し、中間幅の文字折り返しを修正しました。実装都合だけでカード表示へ変えず、Pencil正本を再確認して1024pxでは優先列の表を維持しました。

## AIをどう活用したか

AIは、要件と制作記録の整理、参考調査の補助、画面案・実装案の作成、コードの生成・修正、静的監査、レスポンシブ確認、商品サムネイル生成に利用しました。

一方で、対象、課題、制作範囲、名称、コピー、ロゴ採用、画面ごとの情報優先度、素材の自然さ、修正の要否は私が確認して決定しました。AIの出力はそのまま採用せず、Pencilと実装のスクリーンショットを確認し、文字の重なり、背景の跡、AIらしい画像表現、中間幅の折り返しを具体的に指摘して修正しています。
